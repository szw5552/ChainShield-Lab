# ChainShield Lab Constitution

## Core Principles

### I. Code Quality and Simplicity
Code MUST be readable, cohesive, and directly tied to a user or PoC outcome. Each change MUST
prefer the simplest design that satisfies current requirements, following KISS and avoiding
speculative abstractions, unused extension points, or framework layers without demonstrated need.
Duplication MAY remain when removing it would create a more complex abstraction than the current
problem justifies. Rationale: ChainShield Lab is a demonstrable security PoC, so clarity and
traceability are more valuable than premature generalization.

### II. Test-First Engineering
TDD is mandatory for production and PoC behavior that can be automated. Developers MUST define the
failing test first, verify the red state, implement the minimum code to pass, and refactor only after
the green state is proven. Unit, integration, contract, or sandbox tests MUST be selected based on the
risk being changed, and any intentionally unautomated behavior MUST have a documented manual
verification path. Rationale: supply-chain defense logic must be reproducible and safe to change.

### III. Behavior-Driven User Value
BDD is mandatory for user-facing behavior and agent decision flows. Specifications MUST express
prioritized user journeys with Given/When/Then acceptance scenarios before implementation planning.
Every user story MUST be independently demonstrable, independently testable, and traceable from
scenario to task to verification evidence. Rationale: demo value depends on observable outcomes such
as allow, deny, evidence collection, and sandbox containment.

### IV. Consistent User Experience and Language
User-facing flows, terminology, decision reasons, and evidence summaries MUST be consistent across
README guidance, generated specifications, plans, tasks, quickstarts, reports, and CLI or agent
outputs. All Spec Kit generated user-facing artifacts, including spec.md, plan.md, tasks.md,
research.md, data-model.md, quickstart.md, checklists, and similar feature documents, MUST be written
in Traditional Chinese (zh-TW). This constitution.md file MUST remain in English. Rationale: a single
language and vocabulary reduce ambiguity during demos and reviews.

### V. Performance and Operational Evidence
Every feature plan MUST define measurable performance, resource, or responsiveness requirements
appropriate to its scope, or explicitly mark them not applicable with rationale. Security gates and
sandbox flows MUST preserve enough structured evidence to diagnose allow or deny decisions without
rerunning the full demo. Changes that add scanning, installation, sandboxing, or report processing
MUST document expected runtime, failure behavior, and log evidence. Rationale: performance and
evidence quality determine whether the PoC is credible and repeatable.

## Quality Gates and Constraints
All feature work MUST pass these gates before implementation:

- Constitution checks MUST confirm TDD, BDD acceptance scenarios, KISS scope control, UX language
  consistency, and performance requirements.
- Tests MUST be planned as mandatory work unless the feature is documentation-only or a documented
  manual verification is more appropriate for the PoC.
- Complexity MUST be justified with the rejected simpler alternative and the concrete risk that
  requires the added design.
- User-facing artifacts generated by Spec Kit MUST use zh-TW; constitution changes MUST use English.
- Security decisions MUST remain evidence-driven, with deny reasons traceable to Snyk, Socket,
  OpenShell, sandbox logs, or documented manual observations.

## Development Workflow
Feature delivery MUST follow this workflow:

1. Specify behavior with prioritized BDD scenarios and measurable success criteria.
2. Plan the smallest viable technical approach and record any complexity exceptions.
3. Write or update tests first, verify they fail, then implement the minimum passing change.
4. Refactor for clarity only after tests pass and the simpler design remains intact.
5. Validate independent user stories, performance expectations, and operational evidence before
   marking work complete.
6. Keep generated feature documents in zh-TW and keep this constitution in English.

## Governance
This constitution supersedes conflicting project practices, templates, and generated plans. Pull
requests, implementation plans, and task lists MUST include an explicit constitution compliance check.
Amendments require a documented rationale, updates to dependent templates or guidance, and a version
change using semantic versioning:

- MAJOR: backward-incompatible principle removals or redefinitions.
- MINOR: new principles, sections, or materially expanded governance requirements.
- PATCH: clarifications, wording fixes, or non-semantic refinements.

Compliance MUST be reviewed before Phase 0 research, after Phase 1 design, and before implementation
completion. If a feature cannot satisfy a principle, the plan MUST document the violation, rejected
simpler alternatives, mitigation, and review owner before work proceeds.
